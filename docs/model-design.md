# Agronomic Risk & Crop Health — Model Design

Staff-level review of the existing model and a target design for risk scoring, crop health, and the
surrounding agronomic metric set.

Status: the analysis reflects the code as of this branch's parent commit (`24f1a48`). The
"Implemented here" section at the end lists what this branch already changes.

---

## 1. Verdict

The engineering around the model is competent — graceful degradation, threadpool offloading for
blocking I/O, feature/artifact decoupling in `ModelManager._align_features`, tracing, a real
Sentinel-2 Statistical API integration. That is a solid platform.

The model itself is not a model. It is a six-line `if/else` rule, re-expressed as a four-estimator
stacked ensemble trained on data generated by that same rule. Everything downstream of it — the
risk score, the probabilities, the SHAP explainer, the calibration layer — inherits that circularity
and reports confidence it has not earned.

This is a recoverable position, and cheaply, because the physical and epidemiological signal the
system needs is computable **without any labels at all**. The redesign below front-loads that
label-free layer, then adds supervision only where real outcomes exist.

---

## 2. What the system does today

```
POST /predict/farmer
  → Postgres: farmer profile + ML profile          (24 survey fields)
  → Open-Meteo: 8-day hourly forecast              (temp, RH, soil moisture, rain)
  → CDSE Sentinel-2 Statistical API: 30-day mean   (NDVI, NDWI, EVI)
  → 27-column frame → HybridSpatiotemporalEnsemble → 3-class prediction
  → risk_score = P(class 2) × 100
```

## 3. Findings

Ranked by impact on decision quality. Each is anchored to a file and line.

### P0-1 — The label is a deterministic function of five features (circular target)

`src/argotech/training/dataset.py:157-164`

```python
if rh_85_consecutive_hrs >= 16 and incubation_hours >= 18 and ndwi < 0.12:  label = 2
elif drought_risk == 1 or ndvi < 0.30:                                      label = 2
elif rh_85_consecutive_hrs >= 12 or ndwi < 0.20:                            label = 1
else:                                                                       label = 0
```

Every input to this rule is also a model feature (`drought_risk` at line 143, `ndvi`/`ndwi` at
149-150, and `rh_85_consecutive_hrs` / `incubation_hours` via `shock_level` at line 120). The
remaining 20 features are `np.random` draws statistically independent of the label
(lines 124-146). So:

- The ensemble is a lossy approximation of an `if/else` an intern could write in one line, at
  roughly 10⁵ times the compute.
- The reported cross-validation F1 measures how well gradient boosting memorises a rule it was
  handed. It is near 1.0 and it is not evidence of anything.
- **Nothing** in the pipeline has ever been validated against a real agronomic outcome.
- `train_powerful_model.py` reported feature importances from this setup. Those importances describe
  the synthetic generator, not agriculture.

This single fact invalidates the accuracy claims for the whole service. It is P0.

### P0-2 — `rainfall_anomaly` means two different things at train and serve time

| | Definition | Range |
|---|---|---|
| Train (`dataset.py:64`) | `six_month_total_rain − 450` | −450 … +400 |
| Serve (`pipeline.py:166`) | `eight_day_total_rain` | 0 … ~60 |

Same column name, disjoint distributions. Every served row lands in a region of feature space the
model never saw. `drought_risk` has the same defect: `total_rain < 200` over six months at training
(`dataset.py:65`) versus `total_rain < 5` over eight days at serving (`pipeline.py:125`).

The current model happens to be blind to it only because the shipped `.pkl` predates the spectral
columns and `_align_features` silently drops what it does not recognise — an accident, not a
safeguard.

### P0-3 — Probability calibration is fitted on its own training data

`src/argotech/models/ensemble.py:78-83`

```python
self.stacking_model.fit(X, y)                 # fit on all of X
self.calibrated_model = CalibratedClassifierCV(self.stacking_model, cv="prefit")
self.calibrated_model.fit(X, y)               # calibrate on the same X
```

`cv="prefit"` exists specifically so calibration can be fitted on a *held-out* set. Fitting it on
the training data teaches the sigmoid to reproduce in-sample scores, which are already near-perfect.
The output is more overconfident than the raw ensemble, not less. Since `risk_score` is exactly
`P(class 2) × 100` (`pipeline.py:368`), the headline number the product surfaces is a
miscalibrated probability of a synthetic label.

### P1-4 — A protected attribute drives a resource-allocation decision

`head_gender` is a model feature (`features/schema.py:25`) in a system whose output ranks farmers
for extension visits, credit referral, and input subsidy. On synthetic data it is noise. Trained on
real survey data it will encode the historical correlation between household headship and
disadvantage, and then *act* on it — routing scarce agronomic support by gender under the cover of a
model score. `household_max_education` carries the same exposure.

Keep both for **measuring** disparate impact across the ranking. Never as inputs to it.

### P1-5 — Hazard and vulnerability are fused into one opaque label

The 27-column frame mixes fast, physically verifiable signals (rainfall, humidity, NDVI) with slow,
socio-economic ones (asset score, credit, transport cost). Consequences:

- Unvalidatable: the weather half is checkable within days; the vulnerability half only against
  harvest outcomes months later. Fused, neither is measurable separately.
- Unactionable: "risk 78" does not tell an extension officer whether to bring fungicide or a loan
  application form.
- Unauditable: see P1-4.

### P1-6 — Validation protocol is wrong for geospatial data

`dataset.py:184` uses `StratifiedKFold(shuffle=True)`. Neighbouring coordinates share weather,
soil and satellite scenes; random splits leak information from training to validation folds and
inflate the score. Geospatial models need **spatially blocked** CV (leave-one-region-out) and
**forward-chaining temporal** splits (train on seasons ≤ *t*, test on *t+1*). The question the
product needs answered is "does this work in a district and a season we have never seen", and random
K-fold cannot answer it.

Weighted F1 is also the wrong metric: the operational task is "which 50 farmers does an agent visit
this week", which is ranking, not classification. Evaluate with precision@k / recall@k and
cost-weighted utility.

## 4. Target design

### 4.1 Start from the target definition, not the model

No amount of model architecture fixes an invented label. Three label sources, in the order they
become available:

| Tier | Label | Source | Latency | Volume |
|---|---|---|---|---|
| **T0 — proxy** | NDVI/NDRE anomaly z-score vs. the field's own history and its agro-ecological peer cohort | Sentinel-2/1, computed | days | unlimited, day one |
| **T1 — event** | Confirmed stress/disease event: agent field inspection, photo diagnosis, farmer report confirmed by an agent | app + extension workflow | weeks | hundreds/season, grows |
| **T2 — outcome** | Realised yield (t/ha) and loss fraction vs. expectation | harvest record, aggregator receipt | one season | the ground truth |

T0 is available immediately and is what the label-free layer below scores against. T1 is what makes
disease classification real, and it must be **instrumented now** — every advisory the service issues
should be reconcilable against what the agent found. T2 is the target the risk score is ultimately
calibrated to.

The decisive engineering task of the next quarter is not modelling. It is **closing the feedback
loop** so T1 and T2 accumulate. A system that issues 10 000 advisories a season and records zero
outcomes will still have no training data next year.

### 4.2 Layered architecture

Replace the single 3-class classifier with four layers, each separately testable and separately
deployable.

```
L0  Data & features   point-in-time-correct store; Sentinel-2 + Sentinel-1 + ERA5/Open-Meteo + survey
L1  Agronomic state   label-free physics & epidemiology  →  Crop Health Index, water balance, DSV, GDD
L2  Learned models    supervised, only where labels exist →  yield anomaly, disease event, uncertainty
L3  Risk composition  Risk = Hazard × Exposure × Vulnerability  →  score + expected loss
L4  Decision layer    ranking, thresholds, advisory generation, feedback capture
```

The critical property: **L1 works with zero labels**, so the product ships useful, defensible
numbers on day one, and L2 upgrades individual components as labels arrive without a rewrite.

### 4.3 L1 — Agronomic state (implemented in `argotech/domain/`)

Published relationships, not fitted parameters. They transfer across regions, need no training data,
and give L2 features that already carry agronomic meaning.

**Crop Health Index** (`domain/indices.py`) — transparent weighted composite on 0-100:

| Sub-score | Basis | Why |
|---|---|---|
| Vigour | VCI: current NDVI within the field's own historical range (Kogan 1990) | absolute NDVI is meaningless across crops and agro-ecologies |
| Moisture | NDMI (B08/B11) mapped over the field-relevant range | canopy water content, the earliest visible drought signal |
| Anomaly | logistic of the NDVI z-score vs. the peer cohort | separates "this field is struggling" from "the whole district is dry" |

Deliberately *not* a learned model: no labels required, stable across seasons, auditable by an
agronomist. It measures **state**, not risk — the two must not be conflated.

**Index selection** matters more than model choice here:

- **SAVI** instead of NDVI on sparse early-season canopy — smallholder plots are soil-dominated for
  the first six weeks and NDVI reads that soil as crop failure.
- **NDRE** (red-edge, B05) once canopy closes — NDVI saturates above LAI ≈ 3, NDRE does not, and it
  is the index that actually tracks nitrogen status mid-season.
- **NDMI** (B08/B11) for water content. The repo's "NDWI" is already this formula under the wrong
  name; McFeeters' NDWI (green/NIR) is a water-body index, not a crop index.

**Agronomic models** (`domain/agronomy.py`):

- **GDD with an upper cutoff** → cumulative thermal time → **phenology stage**. Replaces the
  hard-coded stage string. Stage drives everything downstream: crop coefficient, heat sensitivity,
  which advisories are even actionable.
- **FAO-56 water balance**: `deficit = Kc(stage) × ET0 − rainfall − irrigation`. Open-Meteo returns
  `et0_fao_evapotranspiration` directly, so this costs one extra query parameter, not a
  Penman-Monteith implementation. Total rainfall alone — what the service uses today — cannot
  express water stress, because 40 mm is generous at emergence and a drought at flowering.
- **Longest dry spell** within the window. Seasonal totals hide the two-week gap at silking that
  actually destroys the maize crop.
- **Heat stress days** above the pollen-viability threshold, counted only during flowering.
- **Wallin/BLITECAST disease severity values**: leaf wetness duration × mean temperature during the
  wet period, accumulated to a published spray threshold (18 DSV). This is the validated version of
  what `rh_85_consecutive_hrs` and `incubation_hours` are groping toward — same inputs, real
  thresholds, and an output that maps to an action.
- **Fall armyworm degree-days** (base 10 °C, ~390 DD/generation). The dominant maize pest across SSA
  since 2016, and degree-day accumulation is how scouting is timed.

### 4.4 L2 — Learned models

Add supervision only where labels exist, one component at a time.

| Model | Target | Data | When |
|---|---|---|---|
| Yield anomaly | log(yield / cohort expectation) | T2 harvest records + L1 features + RS time series | after one season |
| Disease event | P(confirmed event in next 14 d) | T1 agent confirmations | ~500 confirmed events |
| Crop type / area | crop class per field | WorldCereal + Presto embeddings, fine-tuned on local ground truth | now — pretrained |

**Tabular estimator: gradient boosting, single model.** Not a four-way stack under a logistic
meta-learner. On tabular data of this size the stack buys a fraction of a point of AUC and costs
interpretability, latency, and four times the retraining surface. LightGBM or XGBoost with
early stopping on a spatially blocked validation set. If the stack ever justifies itself on a
*correct* validation protocol, keep it — it currently justifies itself on a rule it memorised.

**Remote-sensing representation: use pretrained geospatial encoders, do not train a vision model.**
The 2025-26 state of the art here is genuinely useful and mostly free:

- **Presto** — lightweight pretrained model for *pixel-level time series*, purpose-built for
  smallholder settings with few labels. Presto embeddings + a gradient-boosted head is the
  WorldCereal recipe and is the right default for this problem shape.
- **AlphaEarth / Satellite Embeddings** (Google, 2025) — precomputed 64-dimensional annual
  embeddings per 10 m pixel in Earth Engine. A feature join, not a training job.
- **Prithvi-EO-2.0** (NASA/IBM), **Clay v1**, **TerraMind** (ESA/IBM) — full geospatial foundation
  models when a segmentation or field-boundary task appears.

The lesson: the encoder is a solved, downloadable component. Spend the labels on the head.

**Sentinel-1 SAR is not optional.** SAR penetrates cloud. Optical-only sensing fails during the
rainy season, which is precisely when disease pressure peaks — the system is blind exactly when it
is needed. Add S1 VV/VH backscatter and the RVI, and consider Harmonized Landsat-Sentinel (HLS) for
2-3 day effective revisit.

**Uncertainty: conformal prediction, not `CalibratedClassifierCV` on training data.** Split-conformal
gives distribution-free coverage guarantees on a held-out calibration set, in about thirty lines,
with no assumption about the score's shape. Every risk number surfaced to a farmer should carry an
interval, and low-confidence predictions should route to a human rather than to an SMS.

### 4.5 L3 — Risk composition (implemented in `argotech/domain/risk.py`)

```
Risk = Hazard × Exposure × Vulnerability
```

The IPCC AR5/AR6 framing, and the standard in agricultural early warning. Each term is computed and
validated separately, then composed by arithmetic anyone can check.

**Hazard** ∈ [0,1] — physical probability/intensity of an adverse event, from L1. Drought, disease
and heat components combined with a **noisy-OR** (`1 − Π(1 − hᵢ)`), so hazards compound: two
independent 0.4 hazards give 0.64, not 0.4. A field facing both drought and blight *is* worse off
than one facing either.

**Exposure** — value actually at stake: `area × expected_yield × price`. Absolute, in currency. This
is the term that makes scores rankable *across* farmers, which is what a triage queue needs and what
a softmax probability cannot provide.

**Vulnerability** ∈ [0,1] — inability to absorb the shock, from irrigation, extension access, credit,
input use, diversification, assets, market access. Built **only** from attributes a farmer or a
programme can change. Protected attributes raise a `ValueError` rather than being quietly ignored —
a fairness constraint that lives only in a comment gets violated the first time someone adds a
column.

Vulnerability is applied as a modulation `(0.5 + 0.5v)` rather than a raw multiplier: a
well-resourced farm facing a severe hazard must still be flagged. A farmer with irrigation and credit
still loses the crop to late blight if nobody tells them to spray.

Two outputs, because they answer different questions:

- `risk_score` (0-100) — expected **loss rate**. Comparable across farms of any size. The number a
  farmer sees.
- `expected_loss` (currency) — `value_at_risk × loss_rate`. What a triage queue ranks by, and what
  makes the programme's return on an extension visit measurable.

### 4.6 L4 — Decision layer

- **Ranking, not classification.** Optimise and report precision@k for the k an agent can actually
  visit. Report cost-weighted utility: a missed outbreak costs a season; a false alarm costs a
  motorbike trip. That ratio, not F1, sets the threshold.
- **Advisory generation is the only place an LLM belongs.** Translating structured model output
  (stage, dominant hazard, DSV total, deficit) into a farmer-readable message in Hausa, Swahili or
  Amharic is a genuine language task. Generating the *risk number* is not. Keep the LLM strictly
  downstream of the numbers, and template-check its output against the structured facts.
- **Capture the response.** Every advisory records what was recommended, whether an agent went, what
  they found. That is the T1 label stream, and it is worth more than any modelling work.

## 5. Metric catalogue

What the service should compute and expose, grouped by what it answers.

**Canopy state** — NDVI, EVI, SAVI (sparse canopy), NDRE (post-closure N status), NDMI (water
content), fAPAR/LAI, VCI, per-field anomaly z-score, peer-cohort percentile, phenology stage,
start-of-season / peak / senescence dates from the smoothed NDVI series, **Crop Health Index**.

**Water & climate** — cumulative rainfall, rainfall anomaly vs. climatological normal for the same
window, SPI-1/3/6, SPEI, ET0, crop water requirement `Kc × ET0`, water deficit, water satisfaction
index, soil moisture anomaly, longest dry spell, onset-of-rains deviation.

**Thermal & stress** — GDD accumulation, heat stress days above the flowering threshold, cold/frost
events where relevant, diurnal range.

**Biotic pressure** — leaf wetness duration, accumulated DSV vs. spray threshold, days since last
spray, fall armyworm degree-days and generation count, regional outbreak proximity from confirmed
T1 reports.

**Vulnerability & impact** — coping-capacity sub-scores and named gaps, value at risk, expected loss,
insurance/credit coverage, distance to input market.

**Model health** (dashboarded, not served) — feature drift (PSI/KL) per feature, prediction
distribution drift, calibration error against T1/T2 as they land, coverage of the conformal
intervals, share of predictions served from the synthetic-index fallback, precision@k on the
realised agent-visit outcomes.

That last group is what turns this from a demo into a system. Because labels arrive months late,
**drift monitoring is the only near-real-time signal that the model has silently broken.**

## 6. Validation protocol

Non-negotiable, and the reason to distrust every accuracy number currently reported:

1. **Spatially blocked CV** — leave-one-district-out. Neighbouring fields share weather and scenes;
   random folds leak.
2. **Forward-chaining temporal splits** — train on seasons ≤ *t*, test on *t+1*. Never shuffle across
   seasons.
3. **Point-in-time-correct features** — every feature value as it was known at prediction time. A
   feature store that lets a 30-day NDVI mean computed *after* the event leak into training will
   produce a model that is excellent offline and useless online.
4. **A baseline that must be beaten** — the L1 rule set. If the learned model cannot beat transparent
   agronomy on blocked CV, ship the agronomy. It is cheaper, explainable, and it transfers.
5. **Fairness slice report** — precision@k and expected-loss coverage sliced by household headship,
   landholding size, and district, published with every model version.
6. **Release gate in CI** — a model that does not beat the incumbent *and* the L1 baseline on blocked
   CV, with calibration error under threshold and no fairness slice regression, does not promote.

## 7. Repository structure

Restructured in this branch from `src/services/inferenceService/app/...` (five levels to reach a
module, and the package name told you nothing) to a domain-oriented layout:

```
argotech-ai/
├── pyproject.toml              # single dependency source; replaces requirements.txt
├── docs/model-design.md        # this document
├── src/argotech/
│   ├── config.py
│   ├── domain/                 # PURE: no I/O, no network, no DB. The agronomy lives here.
│   │   ├── indices.py          #   spectral indices, VCI, anomaly, Crop Health Index
│   │   ├── agronomy.py         #   GDD, phenology, FAO-56 water balance, DSV, FAW
│   │   └── risk.py             #   Hazard × Exposure × Vulnerability composition
│   ├── data/                   # I/O adapters, one per upstream
│   │   ├── sentinel.py         #   CDSE Statistical API (+ 12-month history)
│   │   └── db.py
│   ├── features/               # feature schema + point-in-time builders
│   ├── models/                 # estimators, fusion, registry/loading
│   ├── serving/                # FastAPI app, routers, request/response schemas, pipeline
│   └── training/               # dataset construction, training entrypoints
└── tests/test_domain.py        # runnable self-check for the whole domain layer
```

The load-bearing boundary is `domain/`. It is pure functions over plain values: no network, no
database, no model artifact. That is what makes the agronomy unit-testable in milliseconds, reusable
from the training pipeline and the serving path without duplication, and portable to a batch job or
an edge device later. Everything else is an adapter around it.

**Still to do** (deliberately not in this branch, each needs its own change):

- Model artifacts out of git and out of the image — 118 MB of byte-identical pickles plus a 13 MB
  explainer are tracked today. Pull from GCS/registry at startup, keyed by version.
- **Artifact format**: `joblib` pickles bind to scikit-learn's exact internal module layout, which is
  why `requirements.txt` had to pin four packages and why a bump breaks `joblib.load` at runtime.
  Export to ONNX (or XGBoost's own JSON) and the pin disappears along with the whole class of
  failure.
- Image tags by commit SHA, not date, so a running container is traceable to a revision.
- Drop the direct Postgres coupling: this service reads the Kotlin backend's tables directly, so a
  backend migration can break inference silently. The backend should pass the farmer payload.
- Feature store with point-in-time correctness, once T1/T2 labels start accumulating.

## 8. Roadmap

**Phase 1 — stop reporting numbers that are not real** (days)
Ship the L1 layer as the primary output. Real Crop Health Index. Real phenology. Real water balance
and DSV. Label the untrained fusion score as a diagnostic or remove it. Fix the `rainfall_anomaly` /
`drought_risk` train-serve skew as part of a retrain, never on the serving side alone.

**Phase 2 — instrument the feedback loop** (weeks, and the highest-leverage work in this document)
Persist every prediction with its full feature vector and a stable ID. Record agent outcomes against
it. Add harvest capture. Without this, phase 3 is impossible next season too.

**Phase 3 — supervised models where labels justify them** (one season)
Yield-anomaly regression on T2. Disease-event classification on T1. Spatially blocked and
forward-chained validation. Conformal intervals. Release gates in CI. Retire any L1 component the
learned model beats on blocked CV — and keep the ones it does not.

**Phase 4 — representation and coverage** (ongoing)
Sentinel-1 SAR for cloud-season continuity. Presto or AlphaEarth embeddings as features. Per-field
boundaries so peer cohorts become spatial rather than temporal. Drift monitoring in production.

## 9. Retraining results

The model was rebuilt on real data (`argotech.training.dataset` → `argotech.training.train`) and
evaluated under the protocol in §6.

**Dataset** — 7,527 samples, 185 sites, 6 clusters, 2022-09-10 … 2026-06-22. Features: ERA5 daily
reanalysis over the preceding 90 days passed through `argotech.domain`, plus the Sentinel-2 canopy
state. Label: peer-standardised NDVI anomaly one 30-day interval ahead. Class balance 69.4 / 16.8 /
13.7 %.

### Spatially blocked (leave-one-cluster-out)

| Held-out cluster | n | macro F1 | ECE | **P@25** | majority F1 | persistence F1 | persistence P@25 |
|---|---|---|---|---|---|---|---|
| Benue_River_Basin | 935 | 0.365 | 0.067 | **0.640** | 0.274 | 0.400 | 0.440 |
| Ethiopian_Highlands | 1443 | 0.403 | 0.116 | **1.000** | 0.275 | 0.437 | 0.360 |
| Kaduna_Grain_Belt | 1250 | 0.475 | 0.088 | **0.720** | 0.258 | 0.523 | 0.520 |
| Kano_Sudan_Savannah | 1412 | 0.501 | 0.112 | **0.840** | 0.280 | 0.575 | 0.760 |
| Kenya_Rift_Valley | 1175 | 0.379 | 0.039 | **0.520** | 0.271 | 0.396 | 0.200 |
| Tanzania_Morogoro | 1312 | 0.347 | 0.134 | 0.440 | 0.279 | 0.366 | **0.480** |
| **mean** | | 0.412 | 0.093 | **0.693** | 0.273 | 0.450 | 0.460 |

### Forward-chaining temporal

| Split | n | macro F1 | ECE | P@25 | majority F1 | persistence F1 | persistence P@25 |
|---|---|---|---|---|---|---|---|
| train < 2024-09-30 | 147 | 0.430 | 0.099 | 0.560 | 0.281 | 0.427 | 0.560 |
| train < 2025-03-28 | 171 | 0.400 | 0.150 | 0.440 | 0.294 | 0.514 | 0.560 |
| train < 2025-09-24 | 136 | 0.380 | 0.067 | 0.440 | 0.269 | 0.306 | 0.480 |

### What this says

1. **On the operational metric the model now clearly beats persistence.** Mean spatial P@25 is
   0.693 against 0.460, winning 5 of 6 clusters. Precision@k is what the product actually needs —
   an agent visits *k* farms this week and what matters is how many of those visits land on a field
   that needed one. Ethiopian Highlands is a clean 1.000 against 0.360.
2. **On macro F1 it still loses to persistence** (0.412 vs 0.450 mean). The two metrics disagree
   because F1 rewards getting the ordinal class boundaries right across the whole distribution,
   while P@k only cares about the top of the ranking. The product ranks; F1 is the diagnostic.
3. **Calibration is good** — mean ECE 0.093, best fold 0.039.
4. **The weather block is no longer inert.** With 7,527 samples instead of 4,215, permutation
   importance on held-out ground reordered completely: `ndmi` +0.025 and `evi` +0.022 now lead,
   `ndvi_z_peer` fell to +0.012, and the agronomy carries real signal — `et0_90` +0.009,
   `dry_spell_30` +0.008, `diurnal_range_30` +0.006, `radiation_90` +0.005, `stage_kc` +0.003.
   At the smaller sample size the model was a smoothed persistence model; it is not one now.
5. **Temporal generalisation is the weak axis.** The model trails persistence on P@25 across all
   three forward-chaining folds (0.480 vs 0.533), on 136-171 samples each. Predicting *next month*
   at a site is still harder than ranking *across* sites today.

### Why the earlier run looked worse, and what still limits this

The first build reached only 113 of 192 sites because Open-Meteo's archive quota ran out mid-backfill.
The 4,215-sample result — model indistinguishable from persistence, weather features contributing
nothing — was a sample-size artefact, not a property of the task. Worth remembering when reading any
single evaluation: the honest protocol correctly refused to endorse the model, and correctly changed
its answer when the data arrived.

Remaining limits, in order:

- **Label.** A peer-relative NDVI level 30 days out is still partly dominated by persistent
  field-level differences. A label on the *change*, or a real T1/T2 outcome, is the next step up.
- **Resolution.** ERA5 is a ~9-25 km grid; sites inside a cluster can share cells. CHIRPS (5 km) and
  SMAP soil moisture would sharpen the weather block further.
- **Cloud gaps.** 185 of 192 sites survived this time, but the gaps still cluster in the rainy
  season. Sentinel-1 SAR is the fix.

### Decision

The retrained model **ships as the vegetation-hazard term** in the `domain.risk` composition. It has
now earned that role on evidence rather than on calibration alone: it ranks better than persistence
on the metric the product uses, it is well calibrated, and it draws on the agronomy rather than
echoing the current anomaly. Promoting it to the primary risk score still requires beating
persistence on temporal generalisation, which it does not yet do.

## 10. Serving architecture: batch features + audit trail

Two changes that make the rest of the roadmap possible.

### Features off the request path

`argotech.jobs.precompute` runs nightly, single-instance, and writes one `field_features` row per
registered field. `/predict` reads that row; it falls back to computing live only when no fresh row
exists (a field registered this morning still gets a prediction today, it just pays the latency
once). `field_features.computed_at` older than 48 h is refused rather than served.

Both paths call the *same* `pipeline.gather_upstream`, which is what makes a precomputed prediction
and a live one the same computation — verified by a parity check that round-trips a real
`gather_upstream` result through JSON and asserts byte-identical responses.

Why it matters: every prediction previously made three blocking calls to two free public APIs, one
of which (the 4-year rainfall climatology) took seconds on a cache miss. A single training backfill
exhausted Open-Meteo's daily quota; at farmer volume that is a daily outage. Batching also bounds
the upstream call rate to one pass per field per night instead of unbounded fan-out driven by
traffic.

The job reports a `degraded_rate` — the share of fields with no cloud-free Sentinel-2 scene, and so
no canopy signal and no learned-model contribution. That is the quality metric to alert on, and it
is invisible in any conventional latency/error dashboard.

```
0 2 * * *  python -m argotech.jobs.precompute        # nightly, one instance
```

### Predictions and outcomes

`predictions` stores every prediction with the exact feature vector, model version and
`feature_source` that produced it, so a decision can be explained after the fact, reproduced, and
joined to what happened. The response carries the row's `prediction_id`.

`POST /outcomes` takes that id back with what an agent found, what was diagnosed, or what was
harvested. `store.label_join` is the query that pairs them. `GET /outcomes/label-count` exposes the
count, because "how many labels do we have" is the number that decides when phase 3 becomes
possible and it should be on a dashboard, not discovered by a quarterly query.

Persistence never fails a prediction: losing the audit row is bad, refusing the farmer's forecast
because the audit table is unavailable is worse. If the job has never run and the tables do not
exist, predictions still serve and the write is logged and skipped.

  serving. A feature cannot mean two things if it is defined once.
